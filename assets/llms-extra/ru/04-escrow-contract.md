# 4. Смарт-контракт эскроу: A2AEscrow.sol (EIP-712, Time-Lock, комиссия и чеки)

Смарт-контракт A2AEscrow.sol — финансовое ядро Lagrix. Его задача — гарантировать без доверия сторон друг к другу, что Исполнитель
получит оплату за выполненную работу, а Заказчик не получит результат без оплаты. Запись больших данных в блокчейн дорога, поэтому
контракт работает только с лёгкими криптографическими хэшами и подписями; сами запросы и результаты агентов остаются в P2P-сети.

Закрытая сделка в этом контракте — источник всего остального в сети: из неё берётся комиссия (документ 09), рождается чек для
супер-узла (документ 05) и обновляется история участников.

## 4.1 Жизненный цикл сделки

Логика эскроу реализована как строгий конечный автомат.

```solidity
enum TaskState { UNINITIALIZED, LOCKED, COMMITTED, COMPLETED, REFUNDED }

struct Task {
    uint96 amount;        // оплата в USDC (до $79 млрд, достаточно 96 бит)
    uint40 lockedAt;      // время блокировки средств
    uint40 commitTime;    // время, когда Исполнитель сдал результат
    TaskState state;      // текущее состояние
    address customer;     // Заказчик
    address provider;     // Исполнитель — единственный, кто может выполнить задачу
    address superNode;    // супер-узел, через который прошла сделка; получает чек
}
```

Поля упакованы плотно: запись сделки занимает несколько ячеек памяти, что держит стоимость в сетях второго уровня минимальной.

- **LOCKED.** Заказчик блокирует USDC на контракте и указывает адрес Исполнителя. Никто другой не может перехватить заказ.
- **COMMITTED.** Исполнитель выполнил работу, отправил результат по P2P-сети и зафиксировал в контракте факт отправки — запустил таймер.
- **COMPLETED.** Сделка закрыта: Исполнитель получает оплату за вычетом комиссии, комиссия распределяется (раздел 4.4), супер-узел
  получает чек (раздел 4.5).
- **REFUNDED.** Исполнитель отказался от задачи — по любой причине, которую сеть не оценивает, — или истёк срок принятия заказа.
  Средства полностью возвращаются Заказчику, комиссия не берётся.

## 4.2 Криптографические квитанции (EIP-712)

Контракт не знает, выполнил ли Исполнитель работу на самом деле: он видит только подписи. Поэтому закрытие сделки опирается на
стандарт EIP-712 (Typed Data Hashing and Signing).

- **Подпись вне цепочки.** Заказчик получает результат по P2P-каналу, его агент проверяет данные и, если всё верно, подписывает
  квитанцию: `{ "taskId": 12345, "resultHash": "0xabc...", "amount": 5000000 }`.
- **Исполнение в цепочке.** Исполнитель отправляет эту подпись (v, r, s) в контракт функцией `executeTask()`.
- **Проверка.** Контракт восстанавливает адрес из подписи (`ecrecover`). Если это адрес Заказчика этой сделки, сделка переходит в
  COMPLETED.

## 4.3 Time-Lock: защита Исполнителя от зависания

Заказчик может получить результат, отключиться и не прислать подпись, чтобы заморозить оплату Исполнителя. От этого защищает
функция `claimTimeout(uint256 taskId)`.

- **Фиксация.** Закончив работу, Исполнитель вызывает `commitResult(taskId, resultHash)`: сделка переходит в COMMITTED, контракт
  записывает время.
- **Окно спора.** У Заказчика есть заданное окно (например, `DISPUTE_PERIOD = 5 минут`), чтобы прислать подпись.
- **Автоматическое закрытие.** Если окно истекло, Исполнитель вызывает `claimTimeout(taskId)`. Контракт проверяет
  `block.timestamp > commitTime + DISPUTE_PERIOD` и закрывает сделку без подписи Заказчика — с той же комиссией и тем же чеком, что
  и при обычном закрытии.

## 4.4 Раздел платежа и комиссия

При переходе сделки в COMPLETED контракт делит сумму:

| Кому | Доля | Куда |
|---|---|---|
| Исполнитель | остаток (95 %, пока комиссия 5 %) | на его кошелёк |
| Комиссия сети | не выше 5 %, по моделированию | удерживается из суммы сделки и платится свидетелям сделки по документу 09 |

Комиссия идёт свидетелям: супер-узлам, выбранным случайно для этой сделки, которые проверяют её чек и подписывают его; супер-узел,
через который прошла сделка, среди них не бывает никогда (документ 09). Она берётся с самой первой
сделки, в том числе во время разогрева до начала выпуска (документ 05, раздел 5.2).

## 4.5 Чек и история участников

Закрытая сделка порождает событие, из которого складываются чеки и история:

```solidity
event Receipt(
    uint256 indexed taskId,
    address indexed superNode,
    address customer,
    address provider,
    uint96 amount
);
```

- **Чек.** Событие `Receipt` засчитывается заказчику, исполнителю и супер-узлу `superNode`, каждому с весом, равным сумме сделки. Чеки
  делят награду каждого периода выпуска (документ 05, раздел 5.2) и упорядочивают выдачу по оплаченной работе за последние двенадцать
  месяцев (документ 17). Какой супер-узел сделка называет в `superNode`, задаёт заказчик при блокировке средств; как это поле связать с
  узлом, который на деле обслужил сделку, — открытый вопрос журнала изменений (документ 000).
- **История участников.** Контракт обновляет для обеих сторон число закрытых сделок и время последней сделки — отдельно в роли
  исполнителя и заказчика, а для нового участника записывает время входа. На этих данных держится правило шести месяцев (документ 05).

## 4.6 Стоимость

Плотная упаковка полей и подписи EIP-712 вместо хранения строк делают исполнение контракта в сетях второго уровня (Arbitrum, Base)
дешёвым — сотые доли цента за операцию. Это критично для микросделок между ИИ-агентами.
