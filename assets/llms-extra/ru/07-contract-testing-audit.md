# 7. Тестирование и аудит смарт-контрактов: Foundry, Slither и фаззинг

Смарт-контракты Lagrix работают с настоящими деньгами (USDC) и монетами $LGX. Ошибка в контракте опасна: контракты неизменяемы, без ключа
администратора и ключа обновления (документ 18), поэтому развёрнутый контракт нельзя исправить вовсе — ошибку закрывает только новая
версия, на которую переходят участники. Поэтому каждый контракт до развёртывания проходит трёхслойную проверку: тесты Foundry, фаззинг
инвариантов и статический анализ Slither.

| Контракт | Что делает | Документ |
|---|---|---|
| A2AEscrow.sol | сделки, квитанции, Time-Lock, удержание комиссии, событие `Receipt` | 04 |
| FeeDistributor.sol | котёл комиссий каждого периода и его деление поровну между супер-узлами, прошедшими минимум качества | 09 |
| PeriodIssuance.sol | порог разогрева, часть «доступность» (доля остатка за период), часть «работа» (счётчик V с половинным объёмом и ограничителем скорости), раздел по чекам | 05 |
| SearchVouchers.sol | предоплаченные балансы и обналичка пачек расписок за поиск по фиксированной цене | 17 |
| LagrixToken.sol | монета, предел выпуска, правило шести месяцев, раздел награды периода | 05 |
| SuperNodeDeposits.sol | залоги, выбытие, штрафы, ложные доносы | 06 |
| FeedbackRegistry.sol | отзывы обеих сторон, привязанные к закрытым сделкам, с весом — сетевая часть, делённая на 10, — по элементу и роли | 17 |

## 7.1 Юнит- и интеграционные тесты (Foundry)

Тесты Foundry пишутся прямо на Solidity и выполняются со скоростью скомпилированного кода. Ключевые сценарии:

- `test_A2AEscrow_StateTransitions()` — переходы LOCKED → COMMITTED → COMPLETED и отказ в недопустимых вызовах (например,
  `claimTimeout()` до истечения окна спора).
- `test_EIP712_SignatureReplay()` — подпись нельзя использовать повторно с другим `taskId` или nonce.
- `test_FeeSplit_95_5()` — при закрытии комиссия — ровно постоянная ставка (5 %, пока её не определит моделирование, и не выше 5 %), исполнитель получает остаток; при возврате комиссия не берётся.
- `test_FeePool_EqualShares()` — комиссии периода уходят в его котёл и делятся поровну между супер-узлами, прошедшими минимум качества; стороны сделки и не прошедшие минимум не получают ничего; на следующий период ничего не переносится.
- `test_WarmUp_NoIssuanceBeforeThreshold()` — до порога оплаченного объёма и минимального числа супер-узлов награда не выпускается; чеки разогрева потом ничего не приносят.
- `test_SearchVoucher_ExactPrice()` — расписка на любую сумму, кроме фиксированной цены, отклоняется, а использованный номер нельзя обналичить снова.
- `test_Review_Weight()` — отзыв требует завершённой сделки, по одному от каждой стороны, и весит сетевую часть, делённую на 10; второй отзыв той же стороны на ту же сделку отклоняется.
- `test_SixMonthRule()` — перевод монет раньше 180 дней после входа отклоняется, после — проходит.
- `test_PeriodReward_Split()` — 50 % супер-узлам и 30 % агентам-исполнителям по весу чеков, 20 % поровну супер-узлам, прошедшим минимум качества, с точностью до 1 wei.
- `test_NoAdminFunctions()` — ни одна функция не меняет ставку, цену, порог, половинный объём, долю доступности или ограничитель после развёртывания.
- `test_Downtime_NoSlash()` — недоступный узел не штрафуется, а через 30 дней выбывает с возвратом залога.
- `test_Slashing_HalfToReporter_HalfRemoved()` — половина штрафа доказавшему, половина выводится из обращения.

```solidity
// Пример: Time-Lock в A2AEscrow.t.sol
function test_CannotClaimTimeoutBeforeDisputePeriod() public {
    vm.prank(customer);
    escrow.lockFunds(taskId, provider, superNode, 100 * 10**6); // блокируем 100 USDC (6 знаков после запятой)

    vm.prank(provider);
    escrow.commitResult(taskId, resultHash);

    // пытаемся забрать деньги через 2 минуты, до истечения 5-минутного окна
    vm.warp(block.timestamp + 2 minutes);

    vm.prank(provider);
    vm.expectRevert(A2AEscrow.DisputePeriodNotExpired.selector);
    escrow.claimTimeout(taskId);
}
```

## 7.2 Фаззинг и инварианты

Юнит-тесты проверяют сценарии, о которых подумал разработчик. Фаззинг подаёт миллионы случайных входов — крайние значения, нулевые
адреса, огромные суммы — и проверяет инварианты, которые не должны нарушаться ни при какой последовательности вызовов:

1. **Платёжеспособность эскроу.** Баланс USDC контракта эскроу не меньше суммы всех заблокированных сделок.
2. **Платёжеспособность комиссий.** Баланс USDC контракта FeeDistributor никогда не меньше невостребованной части котлов периодов.
3. **Предел выпуска.** Всего создано монет не больше 1 000 000 000 LGX.
4. **Доли основателя нет.** Ни один адрес не получает новых монет иначе, как за чеки и минимум качества.
5. **Учёт залогов.** Сумма залогов всех супер-узлов равна общему значению в контракте залогов.
6. **Ограничитель скорости.** За период часть «работа» выпускает не больше постоянной доли своего остатка, а счётчик V не растёт сверх
   объёма, который этот выпуск оплатил.
7. **Две части.** Выпущенное частью «доступность» не превышает 200 000 000 LGX, частью «работа» — 800 000 000 LGX.

```solidity
function invariant_EscrowSolvency() public view {
    assertGe(usdc.balanceOf(address(escrow)), escrow.totalLockedFunds(), "Escrow is insolvent");
}

function invariant_SupplyCap() public view {
    assertLe(token.totalMinted(), 1_000_000_000 * 10**18, "Supply cap exceeded");
}
```

## 7.3 Статический анализ (Slither)

Slither переводит код в промежуточное представление и ищет типовые уязвимости:

- **Повторный вход (reentrancy):** защита — порядок «проверки → изменения → внешние вызовы» и `ReentrancyGuard` от OpenZeppelin.
- **Авторизация через `tx.origin`:** запрещена, Slither предупреждает о любом её использовании.
- **Непроверенные низкоуровневые вызовы:** переводы токенов — только через `SafeERC20`.
- **Переполнения:** встроенные проверки Solidity 0.8+ и строгие типы (`uint96`, `uint40`) при упаковке полей.

## 7.4 Конвейер проверок

Каждое изменение в основной ветке открытого репозитория проходит одну и ту же цепочку:

```
[ push / pull request ]
       │
       ├──> 1. forge fmt --check               (форматирование)
       ├──> 2. slither . --fail-on high|medium  (статический анализ)
       ├──> 3. forge test --gas-report          (тесты и расход газа)
       └──> 4. forge test --fuzz-runs 10000     (фаззинг инвариантов)
```

Если хотя бы один из 10 000 случайных вызовов нарушит инвариант, изменение не принимается.
